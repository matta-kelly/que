# que

que is a generic agent harness. A user asks a question in chat; the agent answers it with the services that user has connected.

It knows nothing about any one service or any one company: everything it can do comes from plugins, and which plugins is decided by a deployment. A deployment is a folder of its own, outside this repo. It starts que, and que mounts the plugins that deployment names. This repo holds no plugin and no deployment.

## How it works

- **Deployments**: one folder per way to start que, kept outside this repo, written against one small contract, the deployment type of the harness schema (`Deployment` in `@mku1tra/que-harness`): its name, a description, and the plugins, agents, loops and models it runs, each by its name. Each agent, loop and model is a file of its own in the deployment's `agents/`, `loops/` and `models/`, found by folder, and each plugin is an npm package of its name, installed in the deployment's folder or one above it, found as Node finds an import. A deployment starts que: its `just start` runs que's `just up` with its own folder, so the deployment names que and que does not name it. Nothing in que's own folder picks a deployment, and que stops at startup when it is handed none. A deployment and its plugins can sit outside que: que gives them `@mku1tra/que-plugin`, `@mku1tra/que-harness`, `zod` and `@mku1tra/basis` (`server/plugin/plugin-contract.md`).
- **Plugins**: one folder per concern, kept in the deployment that uses it: a connector for one service, or a domain across services, which uses connectors' operations and skills by name. A plugin folder is an Agent Plugins 1.0 plugin: its skills (`skills/<name>/SKILL.md`) at the root, with its card (`plugin.json`) written there by `just card` at publish and never committed, and que's own files in `io.github.matta-kelly.que/`. It is written against one small contract (`@mku1tra/que-plugin`, in `server/plugin/`): what the plugin is, the credential it needs, its operations and their roles, what it uses of other plugins, and its skills. To add a capability, add a plugin and name it in the deployment. The harness code does not change. Plugins import no agent framework, so another harness can load the same folder through a thin adapter. The contract is in `server/plugin/plugin-contract.md`.
- **Validation**: each definition is parsed with its type when its file is imported (`defineDeployment`, `defineAgent`, `definePlugin` and the others). Then mount lints the whole deployment as one graph, with the harness schema, which imports the plugin schema: each name links to a thing the deployment gives, each rule holds (a description on every field, each op's role, each name a domain uses, an agent's model and loop named by the deployment, a `maxTokens` within the window), and there is a `SKILL.md` in each skill folder. A `plugin.json` is not read. It stops at startup when anything is wrong, and the error lists each problem, at its file.
- **Model**: a model is a model config: a file of its own in the deployment's `models/`, made with `defineModel` and named in `models` in the deployment's `index.ts` (`Model` in `@mku1tra/que-harness`). It has a `name`, the provider's `id` as `provider:model`, a `window` (the most tokens it takes in), a `maxTokens` (the most it gives in one reply), and an optional `effort`: how hard it thinks, as the provider's own word for a level, sent as `reasoning_effort` (left out, none is sent). An agent config names one with `model`, and a run can name another, with `model` in its `configurable`. A run that names none gets its agent's. que has no model of its own: a deployment names at least one, and one that names none stops at startup. There is no `MODEL` setting: a deployment that sets it stops at startup.
- **Traces**: que sends a trace of each run the agent server makes to the deployment's Langfuse, when its `.env` has `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL` (`server/runtime/src/run/trace.ts`). With none of the three it sends nothing, and with one or two it stops at startup. A trace holds each model call and each tool call of the run, with its input, its output and its times, and says who the run was for (the que user id), its thread (as the session), the agent config it ran under, and the commit que runs from. A Langfuse that refuses a trace or cannot be reached does not stop a run. A failed send is silent unless the `.env` has `OTEL_LOG_LEVEL=error`. The CLI chat is not traced.
- **Loop**: a deployment can say how an agent's loop is run, in a loop config: a file of its own in the deployment's `loops/`, made with `defineLoop` and named in `loops` in the deployment's `index.ts` (`Loop` in `@mku1tra/que-harness`). An agent config names one with `loop`. que has no loop of its own: a deployment names at least one, and one that names none stops at startup. A setting a loop leaves out has que's own value (`LOOP_DEFAULTS`). Every agent is the framework's own agent (LangChain `createAgent`), and each setting that acts adds one middleware to it, so two agents differ only where their configs do. `result.max` acts: a larger tool result is kept in the thread's file store, the chat gets its head, its tail and its path, and the model gets one tool more, `read_file`, to read it. `summarize` acts too: past a share of the model's window, the old part of the chat is replaced by a summary, in the thread too. `args` and `limits` do not act yet. Every agent also gets the repeat guard, which is not a setting of a loop (`server/runtime/src/run/build/repeat.ts`): a tool call that fails 3 times in a row with the same arguments and the same error ends the run, with a message to the user that names the call and the error. It counts over the saved chat, so a repeat across turns counts.
- **Agent**: a deployment can say how its agent runs, in an agent config: a file of its own in the deployment's `agents/`, made with `defineAgent` and named in `agents` in the deployment's `index.ts` (`Agent` in `@mku1tra/que-harness`). A deployment names at least one, and can name several: que has no agent of its own, and a deployment that names none stops at startup. A run names the one it wants, with `agent` in its `configurable`, and a run that names none gets the first. A config has a `name`, its `type` (`agent`), a `description`, its `model` and its `loop`, and a config that leaves one out stops que at startup. Each other field is optional, and says what it is when left out.
    - `plugins`: the names of the plugins the agent gets, out of the ones the deployment mounts. Left out or `[]`: none. A config that names a plugin the deployment does not mount stops que at startup
    - `model`: the name of a model the deployment names. One it does not name stops que at startup
    - `loop`: the name of a loop the deployment names. One it does not name stops que at startup
    - `instructions`: the text that opens the system prompt, in place of que's own role text. Left out, the prompt opens with que's role text
    - `loading`: the name of the way the model is shown its plugins, and when it gets their operations (see Environment legibility): `on-demand` or `eager`. Left out, it is `on-demand`
    - `userInstructions`: `true`, and the system prompt gets the user's own instructions, after the agent's. Left out, it gets none. The text is the one the user saved in Settings > Account, or the content of the file the deployment's `.env` names in `DEV_USER_INSTRUCTIONS` (`server/runtime/src/access/instructions.ts`)
- **Per-user access**: a user connects a service in Settings > Connections. Credentials are stored encrypted in Postgres. A chat's agent is built for its user at the chat's first message, from only the plugins that user has connected then, so a service connected part way through a chat is there from the next chat. An agent config's `plugins` can take plugins out of that set, and can add none.
- **Environment legibility**: the agent does not get every operation up front. Its system prompt explains what a plugin is and lists the ones the user can use; it opens a plugin to see what is inside and loads the operations it needs (`server/runtime/src/assemble/on-demand/`, one config on the shared base in `server/runtime/src/assemble/`). The harness knows the plugin contract, never a specific plugin.

Built with LangChain `createAgent` on the LangGraph dev server, Next.js with assistant-ui, and Postgres.

## Layout

Two apps in one repo. Each has its own `package.json`, lockfile, lint and format config, and neither imports from the other.

- `server/`: the plugin package, the harness package, the backend, the model maker, the runtime and the eval runner
    - `plugin/`: everything a plugin is (`@mku1tra/que-plugin`, published on npm: see [The published packages](#the-published-packages)). In `src/`: the contract (`contract.ts`), its skills and cases, where a plugin's files are (`layout.ts`), how one is read (`read.ts`), its card (`card.ts`), the plugin schema (`schema.ts`), the one check of plugins (`lint.ts`) and the source of plugins for a lint (`source.ts`). Beside `src/`: the Agent Plugins schema a card is checked against (`standards/`), the type notes (`types/`), and `plugin-contract.md`, the plugin contract in words. The plugins themselves are in deployments
    - `harness/`: what runs plugins (`@mku1tra/que-harness`, published on npm: see [The published packages](#the-published-packages)). In `src/`: the harness schema (`schema.ts`): agent, model, loop and deployment, which imports the plugin schema; how code gives a node of it (`define.ts`, with `deployment.ts`, `agent.ts`, `loop.ts` and `model.ts`, each type's node in code and its helpers); how a deployment is read (`read.ts`); its pieces, the source and the lint of its graph (`source.ts`); and the command, `que-harness lint` (`command.ts`). Beside `src/`: the type notes (`types/harness/`)
    - `backend/`: the services the runtime stands on (`identity/`, `users/`, `credentials/`)
    - `chat-model/`: the model maker (`@que/chat-model`): the framework's model for a model config, and que's own model for Beam (`chat-model/beam.ts`). The runtime makes each chat's model with it
    - `runtime/`: the runtime (`@que/runtime`). In `src/`, in the order the work flows, and the only way an import points:
        - `mount/`: reads the deployment and the plugins it names (readDeployment in `@mku1tra/que-harness`), lints them as one graph, and runs on its nodes
        - `card/`: writes a plugin's card from its nodes at publish (`just card`). It reads a plugin as mount does
        - `access/`: the plugins one user can use, their connections, and the users
        - `assemble/`: puts those plugins in front of the model, as one config
        - `run/`: builds a chat's agent for its user at its first run, and keeps it for the chat (`run/chats.ts`), with the settings its loop gives (`run/build/`), sends the trace of each run to Langfuse (`run/trace.ts`), serves the graph and the `/que/*` API, and the CLI
    - `evals/`: the eval runner (`@que/evals`). It reads a deployment's cases and agent configs, runs each case against a running que over HTTP, and prints the runs. When the deployment's `.env` has `QUE_JUDGE`, the name of one of its model configs, that model judges each finished run on the `good` of its case (`evals/src/judge.ts`). When the deployment's `.env` has `LANGFUSE_BASE_URL`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`, it also sends the runs to that Langfuse: the cases as one dataset, and the runs under each agent config as one experiment run (`evals/src/langfuse.ts`). It makes the judge's model with the model maker (`@que/chat-model`), as a run makes its own. It imports the plugin package, the harness package and the model maker, and nothing from the runtime or the backend
    - `tests/integration/`: the tests that mount folders from disk
    - `scripts/recipe-shell.mjs`: writes the shell of each justfile recipe to a file of its own, for the shell set of `scripts/check.sh` to lint. It sits here so the server's lint and format read it
- `ui/`: the chat UI (see `ui/README.md`)
- `templates/deployment/`: an empty deployment to copy: its definition, one agent config, one loop config, one model config (que holds no config of its own: a deployment keeps its own copy), its `.env.example`, and its `justfile`: `start`, `stop`, `logs`, `check` and `eval`
- `scripts/db.sh`: the Postgres container
- `scripts/container.sh`: the dev container, made so it can see a deployment's folder, and the whole git repo the folder is in
- `scripts/check.sh`: the check set of que's own code, which `just check` and the pipeline both run
- `scripts/masked-return.just`: a justfile whose every recipe hides a failure, which the shell set of `scripts/check.sh` must find before it lints the real one

## Setup

Needs podman and [just](https://just.systems). Node runs only inside the dev container, so `node_modules` never lands in this folder: never run npm on the host.

1. Copy `templates/deployment/` to a folder of your own, outside this repo. That folder is your deployment
2. In it, copy `.env.example` to `.env` and fill it in. A deployment's settings and secrets are kept there, and none in this repo
   - que makes a `.que/` folder in it when a start learns a fact of a model: the saved copy of what it learned of the deployment's models (window and price). It is run state, and the template leaves it out of git
3. Name its plugins in its `index.ts`, each by the name of its npm package, found as Node finds an import from the deployment's folder: in the first `node_modules` up from it that holds it. A plugin of the same repo (a repo's own `plugins/`) is linked into that `node_modules` by npm workspaces. que reads, and names, each plugin at its real folder, where its code is, through the link npm made to it. A plugin needs a `package.json` with its name and `"type": "module"`. A plugin keeps que's files in `io.github.matta-kelly.que/`; its card is written by `just card <plugin folder>` when it is published, and never committed. A plugin names the `@mku1tra/que-plugin` it works with as a peer dependency (`"peerDependencies": { "@mku1tra/que-plugin": "^0.6.0" }`), and mount refuses it when que's own `@mku1tra/que-plugin` (`server/plugin/package.json`) is outside that range
4. The UI needs no settings: it talks to the agent server that `just up` starts. To point it at another, copy `ui/.env.example` to `ui/.env.local` and set it there
5. Set `QUE_HOME` to this repo's folder, and run `just start` in the deployment. The first run builds the dev container and installs each app's packages. Starting a deployment from a new folder makes the container again, so that it can see that folder and its repo
6. Open http://localhost:3000 and connect the deployment's services in Settings > Connections

## The published packages

`server/plugin` is published on npm as `@mku1tra/que-plugin`, so a plugin installs it by version, and `server/harness` as `@mku1tra/que-harness`, so a deployment does, with its command, `que-harness lint <deployment folder>`: it lints from the folder that holds the deployment and each plugin's real folder, so a link in a `node_modules` above the deployment, as an npm workspace makes, gives a path inside the folder linted. A folder's own lint that takes the source `deployment` gives a problem at the deployment's `index.ts` for a plugin whose real folder is outside the folder linted, and none of its pieces: lint it with `que-harness lint`, or from a folder that holds it. que's other packages are private.

- npm gets JavaScript: `npm pack` builds each package's `src/` to `dist/` first (`prepack`). Inside que it resolves to `src/` with no build, by que's condition `@mku1tra/que-source` (`server/.npmrc`, and `customConditions` in server/tsconfig.base.json)
- `server/tests/integration/package/` holds each tarball to its file list, and installs it in an empty folder and imports it with plain Node
- a release: set the version in the package's `package.json`, push, then tag that commit `que-plugin-v<version>` or `que-harness-v<version>` and push the tag. `.github/workflows/publish.yml` runs the server set and publishes it, by trusted publishing. que's own tags, `v*`, publish nothing
- by hand, once for each package: its first version is published in the dev container, signed in to npm there as the owner of `@mku1tra`: `podman exec -it -u node -w "$PWD/server/<plugin or harness>" <container> sh -c 'npm login && npm publish'`. Trusted publishing can only be set on a package that exists. Then, on npmjs.com, the package's Trusted Publisher is GitHub Actions, `matta-kelly/que`, workflow `publish.yml`. On GitHub, a tag ruleset lets only an admin make a `que-plugin-v*` or `que-harness-v*` tag

## Commands

From a deployment's folder:

- `just start`: start everything, from that deployment. It runs que's `just up <deployment folder>`. It stops, before starting anything, when another checkout of que is serving, or the agent server's port (2024) or the UI's (3000) is held by anything else: every que's container is on the host network
- `just stop`: stop everything. It runs que's `just down`. The database is shared by every checkout of que, so it keeps running while another one is serving
- `just logs`: follow the agent server and UI logs. It runs que's `just logs`
- `just check`: mount the deployment with no `.env` and no network, from its saved model facts, then type check the deployment's own code and each plugin it lists, wherever the plugin sits, and run their tests, with que's supplied packages handed to all of them. A deployment that would not mount fails, with mount's error: a config path that holds no file, a plugin, loop or model an agent names that the deployment does not list, or a plugin that breaks the plugin schema. A model's window and price come from its file or from the facts a start saved in `.que/`; one in neither fails the check. It runs que's `just check-deployment <deployment folder>`. que's `just check-plugin <plugin folder>` mounts one plugin on its own and checks its code the same way, though not what a domain uses, which only a deployment gives
- `just card <plugin folder>`: write a plugin its card, `plugin.json`, from its nodes, checked against Agent Plugins 1.0: when the plugin is published. The card is never committed. It runs que's `just card <plugin folder>`
- `just eval`: run each case of the deployment's plugins against que, under each of its agent configs, and print what the agent did. que has to be up. `--agent <name>`, one or more times, runs only those configs. The runs act on the real services. When the `.env` sets `QUE_JUDGE` to the name of a model config the deployment lists, that model judges each run that finished: it is asked if the `good` of the case is true of the run, and the report has its verdict (pass, fail or none) and its reason under the run, and how many runs passed under each agent config. A verdict of fail stops nothing. The judge's model is made as a run's is (`@que/chat-model`): any model config a run can use, Beam's included, with its `maxTokens` and its `effort`. A name the deployment does not list stops `just eval` before any run. With no `QUE_JUDGE`, nothing grades a run. When the `.env` has `LANGFUSE_BASE_URL`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`, the runs also go to the deployment's Langfuse, as one experiment run for each agent config, named by the config and the commit of que, with each verdict of pass or fail as the score `good` on its run, and a link to each is printed under the report. With none of the three it only prints the runs, and with one or two it stops before any run. It runs que's `just eval <deployment folder>`

From this repo, for que's own code:

- `just check`: the one way to check que's own code. It runs `scripts/check.sh` in the dev container: types, lint, format, and the unit and integration tests, for each app the change touched, measured against `origin/main` with files not yet committed counted. A change to the justfile or to `scripts/` runs the shell set: shellcheck over the scripts and the shell of each recipe, with its optional check of a masked return on, so a failure inside `$(...)` in a command's arguments, or inside `< <(...)`, fails the check. An exception is a `# shellcheck disable=` line above the command, with its reason. A change to notes and docs alone runs no set, and the command says so. `just check server`, `just check ui` or `just check shell` runs one set, whatever changed. It installs an app's packages again, from the lockfile, when its `package.json` or its lockfile has changed. The pipeline runs the same script (`.github/workflows/checks.yml`)
- `just format`: format every file in both apps with Prettier
- `just card <plugin folder>`: write a plugin its card, `plugin.json`, from its nodes, at its publish. A plugin outside que is handed que's supplied packages, as at mount
- `just check-plugin <plugin folder>`: mount one plugin on its own, with no network, then type check it and run its tests as `just check-folder` does. The folder is a plugin: one with no definition, a definition or cases that break the contract, or a skill that does, fails, with mount's error. What a domain uses is checked by a deployment that lists it
- `just check-folder <folder>`: type check any one folder of TypeScript and run its tests, with que's supplied packages handed to it. It does not ask whether the folder is a plugin: `just check-plugin` checks one
- `just test`: the browser tests (`ui/tests/e2e`) that send no message to the model. `just test-live` runs the ones marked `@live` in their title: each sends a message to the real model, which is paid for and leaves a trace, or needs a real service connected. Both are a manual run, and no part of `just check` or of the pipeline. They need a deployment started, and most were written against one deployment's services and name
- the browser tests have a budget, held by `just check`: a count of tests, and a count of `@live` ones (`scripts/check.sh`). A browser test is for what only the whole running app can show. A decision of the UI's own code goes in a function beside its component, with a Vitest test
- `tests/e2e/trace.sh <deployment folder>`: checks against the real Langfuse that que sends the trace of a run. It needs the deployment started, with the Langfuse settings in its `.env`, and it makes one model call
- `server/tests/smoke/beam.ts`: checks against the real Reflection API that que's model for Beam takes a chat with a tool call and its result. It needs `BEAM_API_KEY`, and it makes two model calls: `podman exec -u node -e BEAM_API_KEY -w "$PWD/server" <container> npx tsx tests/smoke/beam.ts`

Anything else runs in the container: `podman exec -u node -w "$PWD/server" <container> <command>` (or `"$PWD/ui"`). `just _container` prints the container's name.
